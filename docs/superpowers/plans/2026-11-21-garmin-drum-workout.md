# Garmin Drum Workout Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a standalone Garmin Connect IQ app for Forerunner 255 that counts drumming strokes, records a FIT activity with numbered song laps, estimates stroke tempo/regularity, and optionally provides a vibration metronome.

**Architecture:** Keep signal detection and lap math as deterministic Monkey C components, separate from sensor input, activity recording, vibration, and Watch UI. Prove FR255 sensor, FIT, Developer Field, lap, and haptic behavior early; then integrate the components into the app and validate on the actual watch and Garmin Connect.

**Tech Stack:** Monkey C, Garmin Connect IQ SDK, Forerunner 255 device profile (`fr255`), Connect IQ Sensor, ActivityRecording, FitContributor, Attention, and Toybox.Test APIs.

---

## Repository and File Map

The repository currently contains only the approved design spec. The implementation creates:

- `manifest.xml` — app identity, target-compatible minimum API level, and required permissions.
- `monkey.jungle` — Connect IQ compiler inputs.
- `source/DrumWorkoutApp.mc` — app entry point, default settings, and view startup.
- `source/DrumWorkoutView.mc` — live values and lap/session summary rendering.
- `source/DrumWorkoutDelegate.mc` — Start/Pause/Resume/Stop and `KEY_LAP` handling.
- `source/DrumSession.mc` — activity lifecycle and total/lap state transitions.
- `source/DrumMetrics.mc` — total/lap stroke counts, average strokes per minute, estimated tempo, and regularity.
- `source/DrumMetricsTest.mc` — deterministic tests for metric calculations and lap resets.
- `source/HitDetector.mc` — accelerometer peak detection and duplicate-hit suppression.
- `source/HitDetectorTest.mc` — deterministic tests for threshold, re-arming, and refractory behavior.
- `source/AccelerometerInput.mc` — Connect IQ sensor-listener lifecycle and timestamped sample forwarding.
- `source/AccelerometerInputTest.mc` — test for ordered batch-to-detector forwarding.
- `source/DrumSessionTest.mc` — session/lap/pause lifecycle tests.
- `source/ActivityRecorder.mc` — FIT session lifecycle, laps, and developer fields.
- `source/ActivityRecorderProbe.mc` — temporary on-device proof for FIT session calls; remove after Task 5.
- `source/ActivityRecorderTest.mc` — simulator tests for recorder state and FIT field updates.
- `source/Metronome.mc` — optional target BPM and timer-driven vibration pulses.
- `source/MetronomeTest.mc` — tempo-to-period and enabled/disabled behavior tests that do not invoke hardware.
- `source/DrumWorkoutDelegateTest.mc` — key/menu action mapping tests.
- `resources/strings/strings.xml` — visible labels and messages.
- `scripts/test.sh` — builds for `fr255` and runs the Run No Evil test suite.
- `.gitignore` — excludes compiled artifacts and private signing keys.
- `README.md` — SDK setup, build/test commands, device install, limitations, and manual validation.

Keep the files generated by the Monkey C project wizard if they provide required Connect IQ resources or declarations. Do not add a phone app, cloud service, external packages, or CI signing secrets in this MVP.

## Task 2: Implement Lap and Activity Metrics with Tests

**Files:**
- Create: `source/DrumMetrics.mc`
- Create: `source/DrumMetricsTest.mc`

- [ ] **Step 1: Write failing tests for counts, lap reset, average SPM, and interval estimate**

Add `(:test)` functions using `Toybox.Test` assertions. The first test must exercise this exact sequence: begin at `0 ms`, record hits at `500`, `1000`, `1500`, and `2000 ms`; the expected total count is `4`, average at `2000 ms` is `120.0` strokes/minute, and estimated tempo from the three `500 ms` intervals is `120.0 BPM`.

Add tests that a new lap clears only lap values, that fewer than four hits returns `Null` for estimated tempo/regularity, and that uneven intervals lower the regularity score compared with equal intervals.
Also test that `averageSpm(nowMs)` returns `Null` when elapsed lap time is zero and returns `0.0` when elapsed time is positive but there are no hits.

Example test body:

```monkeyc
(:test)
function testFourHitsAtHalfSecondIntervals() as Boolean {
    var metrics = new DrumMetrics();
    metrics.begin(0);
    metrics.registerHit(500);
    metrics.registerHit(1000);
    metrics.registerHit(1500);
    metrics.registerHit(2000);

    Test.assertEqual(4, metrics.totalHits());
    Test.assertEqual(120.0, metrics.averageSpm(2000));
    Test.assertEqual(120.0, metrics.estimatedTempoBpm());
    return true;
}
```

- [ ] **Step 2: Run the tests and confirm they fail**

Run `./scripts/test.sh`.

Expected: the test command reports failures because `DrumMetrics` and its methods do not yet exist.

- [ ] **Step 3: Implement deterministic metric state**

Implement `DrumMetrics` with `begin(startMs)`, `registerHit(timestampMs)`, `beginLap(startMs)`, `totalHits()`, `lapHits()`, `averageSpm(nowMs)`, `estimatedTempoBpm()`, and `regularityPercent()`.

Use total elapsed lap milliseconds for average SPM, so rests between hits count. Return `Null` at zero elapsed time and `0.0` when elapsed time is positive but no hits were detected. For tempo, calculate `60000 / median(inter-hit intervals)` and require at least four hits (three intervals). For regularity, calculate `100 * max(0, 1 - (interval standard deviation / interval mean))`; return `Null` below the same minimum. Reset interval history at each new lap. Do not infer or label these values as synchronization to a song.

- [ ] **Step 4: Re-run the metric tests**

Run `./scripts/test.sh`.

Expected: all metric tests pass, including the no-data and lap-reset cases.

- [ ] **Step 5: Commit the metric component**

```bash
git add source/DrumMetrics.mc source/DrumMetricsTest.mc
git commit -m "feat: calculate drum lap metrics"
```

## Task 3: Implement and Test Accelerometer Hit Detection

- [ ] **Step 1: Write deterministic detector tests**

Use a constructor that accepts an initial dynamic-acceleration threshold of `350 mg` and refractory period of `180 ms`, so device calibration can change the values without changing the state machine.

Emit at most one hit per threshold crossing, re-arm after the signal falls below threshold, and ignore new crossings inside the refractory period. Keep thresholds and the last-sample/last-hit timestamps inside `HitDetector`.

- [ ] **Step 4: Run detector tests**

Run `./scripts/test.sh`.

Expected: all detector tests pass, with exactly the expected count for each synthetic sequence.
